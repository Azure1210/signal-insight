# 测试说明

本文说明 signal-insight 的测试体系：**测什么、怎么跑、契约测试和单元测试各自锁定什么承诺、改代码时要注意什么**。写给改代码的人和跑测试的人。

- 工程规范见《AGENTS.md》；测试目录的存在依据是 D05 的交付要求（数据流水线可验证）。
- 测试只覆盖数据流水线链路（config / geo / dwd / dims / db / quality / pipeline），不覆盖 viz（见第 8 节）。

---

## 1. 一句话概览

- **两类测试**：`test/contract/` 契约测试锁定"模块对下游的承诺"，`test/unit/` 单元测试锁定"单个函数的行为"。
- **规模**：78 个测试 —— 单元 54 个、契约 24 个（含 2 个真实库对账）。
- **零外部依赖**：全部用内存/临时 SQLite + 合成数据，不读 `data/`，任何人 clone 下来就能跑。
- **一行命令**：`python -m pytest`，不需要 editable 安装、不需要设 `PYTHONPATH`。

---

## 2. 怎么跑

在项目根目录：

```bash
python -m pytest                    # 全部测试（约 1 秒）
python -m pytest --run-smoke        # 加跑真实库对账（需要本机有 data/signal.db）
python -m pytest test/contract      # 只跑契约测试
python -m pytest test/unit/test_geo.py -v      # 只跑一个文件
```

- 导入路径由 `pyproject.toml` 的 `[tool.pytest.ini_options] pythonpath = ["src"]` 解决，测试代码里没有 sys.path hack。
- `--run-smoke` 才执行 `test_real_db_smoke.py`；默认永远跳过，CI 和没有 `data/` 的机器不受影响。
- 测试不碰 `data/signal.db`，跑测试不会改坏真实数据。

## 4. 契约测试：锁定了哪些承诺

**契约 = 一个模块对下游的承诺。** 下游按承诺写代码；改实现可以，改承诺就是破坏契约。契约测试从"下游消费者"的视角断言这些承诺，所以它比单元测试更能抓住"重构时悄悄变了行为"的问题。

### 4.1 契约清单

| 契约方 | 承诺 | 测试文件 | 失败意味着 |
|---|---|---|---|
| `dwd.clean_signal` → 下游 | 输出列与顺序 == `DWD_COLS`；ts 是 datetime64、lac_id/cell_id 是 int64；ts 的日期部分全部 == dt；按 (imsi, ts) 排序；剔除记录键 == {"步骤","剔除行数","剩余行数"} 且行数自洽 | `test_dwd_contract.py` | db 写入、D06 停留识别（依赖排序）、notebook 展示会悄悄出错 |
| `db` 写入 → 读回方 | ts 写库后是固定 3 位小数的文本，**毫秒为 0 的行也必须带 `.000`**；同日重跑幂等；不同日互不影响；replace 全量替换、append 只增 | `test_db_contract.py` | 读回时 parse_dates 按第一行推断格式，格式不同的行变空值（D02 需求卡 2.6 的坑，已写成回归测试） |
| `dims` → 下游 | 列 == `DIM_CELL_COLS`；lac_cell 主键唯一；district 永不缺失（"市外"兜底）；site_id 形如 `S\d{5}`；dim_hotspot 五列结构 | `test_dims_contract.py` | join 信令行数被放大；地图/分析缺站点 |
| `pipeline.run_day` ↔ ODS | 4 张 ODS 表结构 == 契约常量；一次运行产出 dwd_signal / dim_cell / dim_hotspot / etl_log 四张表；etl_log 恰 7 步、同批同号、行数正确；同日重跑幂等、日志追加；返回值 == etl_log 表内容 | `test_pipeline_contract.py` | 平台方改了 ODS 结构或流水线漏写表，下游全断 |
| `quality.dq_record` ↔ 表 | dq_check_result 表结构 == `quality.COLUMNS`；同 check_id 覆盖、不同 check_id 共存；表不存在时自动建 | `test_quality_contract.py` | 稽核结果展示读错列、旧记录叠加 |
| 真实库（本地对账） | `data/signal.db` 的 8 张表结构与契约常量一致 | `test_real_db_smoke.py` | ODS 被平台方改结构，流水线会读错列 |

### 4.2 契约常量的来源与更新

`test/contract/ods_schema.py` 里的列结构抄自真实库的 `PRAGMA table_info`（**只抄结构、不抄数据行**，符合 AGENTS.md 1.4、15.3）。

如果平台方改了 ODS 表结构：先跑 `python -m pytest --run-smoke` 看真实库对账报错，确认改动后同步更新 `ods_schema.py`，并检查 `pipeline.py` 里的 `SELECT *` 是否还成立。

### 4.3 etl_log 的步骤顺序是契约

契约测试固化了 run_day 的实际执行顺序：

```
extract_ods → clean_signal → write_dwd → build_dim_cell
→ write_dim_cell → build_dim_hotspot → write_dim_hotspot
```

注意 `write_dim_cell` 在 `build_dim_hotspot` **之前**——因为 `write_dim_hotspot(con, build_dim_hotspot(...))` 的参数要到调用那一刻才求值。这个顺序写进日志表，有人要"优化"执行顺序时，先改契约测试。

## 5. 单元测试：锁定了哪些行为

| 模块 | 锁定的行为 |
|---|---|
| `geo` | haversine：同点为 0、赤道 1 度经度 ≈111.19 km、对称性、数组逐元素、**经纬度传反距离差出几百公里**；rings_from_points：无 ring 列默认单环、seq 乱序自动排序、多环拆分、保持首次出现顺序；point_in_polygons：内/外、**洞（偶数环=外）与飞地（奇数环=内）的奇偶规则**、重叠时先到先得、无匹配返回 None |
| `dwd` | to_local 加 8 小时（UTC 毫秒 → 北京时间）；clean_signal 五步剔除的**每步剔除数**（缺 imsi/lac/cell、IMSI 非 18 位、按 ORIG_COLS 全同才算完全重复、只留指定日）；lac_cell 拼接不出现 `.0`；输出按 (imsi, ts) 排序；缺 tmp0/tmp1 列时抛 KeyError |
| `dims` | 同坐标扇区归并同一 site_id；编号按坐标首次出现顺序 S00001 起；NaN 坐标剔除；区县外标"市外"；lac_cell 重复抛 ValueError；热点中心 = 前 top_n 站点按用户数加权的平均；默认 name="西塔"、radius_m=500 |
| `db` | `_for_storage`：毫秒非 0 保留 3 位、**为 0 补 `.000`**、非时间列不动、不修改原 df；table_exists；三个写函数的行数返回与语义 |
| `quality` | profile：缺失数/率、唯一值、示例值的口径，**首尾空白为空的字符串算缺失**、0 行时缺失率为 0、重复列名按位置统计、list/dict 等不可哈希值按字符串去重、全缺失示例值为 None；dq_record 非法状态抛 ValueError |
| `pipeline` | `_rows` 对 DataFrame/元组/整数/None 的行数口径；step 装饰器：记录步骤名、输入/输出行数、耗时、运行时间，且**不改变函数行为**（参数原样传入、返回值不变）、`functools.wraps` 保留元数据 |
| `config` | find_project_root 命中 marker 文件；缺 marker 时抛 FileNotFoundError（monkeypatch `__file__` 模拟）；口径常量值（UTC_OFFSET_HOURS=8、ANALYSIS_DAY=2018-10-03、DB_PATH 指向 data/signal.db） |

## 6. 测试数据设计

### 6.1 合成 ODS 库（contract/conftest.py）

契约测试用的"迷你 ODS 库"在临时目录里按真实 schema 建 4 张表，数据全合成：

| 表 | 内容 |
|---|---|
| ods_signal | 33 行：24 行 10-03（三组扇区轮流、两个 IMSI）+ 2 行完全重复 + 4 行 10-02 + 缺 imsi / 缺 lac_id / 15 位 IMSI 各 1 行 |
| ods_cell | 3 个扇区：前两个同坐标（→ 同一站点，区县和商圈内），第三个独立坐标（→ 区县外） |
| ods_district_boundary | 1 个正方形区县"和平区"（ring=0，4 个顶点） |
| ods_aoi_v2 | 1 个正方形商圈"西塔"（无 ring 列，只覆盖站点 1） |

锚点数值：`TS_1003 = 1538524800000`（2018-10-03 08:00 北京时间）。脏数据与干净数据混排，使 **33 行 ODS → 清洗后恰好 24 行 dwd**，端到端测试可以精确断言每一步的行数。

### 6.2 为什么不用真实库

1. `data/` 整个不进 Git（AGENTS.md 1.1），测试读它就不能在 CI、别人机器上跑；
2. 测试要**可重复**——真实数据每天被流水线改写，结果不确定；
3. 合规（AGENTS.md 1.4）：合成数据里没有一条真实 IMSI。

真实库的"对账"需求由 smoke 测试单独满足（第 4.1 节）。

## 7. 编写中固化的契约事实

测试编写过程中确认的产品代码行为，已经固化进断言或注释，改代码前先看这里：

1. **etl_log 步骤顺序**：`write_dim_cell` 在 `build_dim_hotspot` 之前（参数求值时机，见 4.3）。
2. **SQLite 存 NULL 读回是 NaN**：step 记录里"输入行数"为 None（con 不是 DataFrame），写库读回后变成 NaN，断言用 `pd.isna`。
3. **pandas 3 的行为变化**（本项目的 pandas ≥3.0）：
   - 字符串列推断为 `StringDtype`（"str"）而不是 `object`——断言字符串用 `is_string_dtype`；
   - `pd.to_datetime` 对混合格式（一行带微秒、一行不带）不再自动推断，直接报错——测试构造混合格式用 `format="mixed"`。**这也正是 `db._for_storage` 契约存在的原因**：写库时统一成 `.fff`，读回才不会踩这个坑。
4. **write_partition 的幂等不是原子的**（先删后写，docstring 里已注明 D11 会遇到）——契约测试锁定的是"正常跑完的结果幂等"，不掩盖这个已知不足。

## 8. 不在测试范围（有意为之）

| 不测的东西 | 原因 |
|---|---|
| viz（theme / maps / layers / heatmatrix / callouts） | 3000 行、大量 matplotlib 渲染断言，脆弱且和 D05 数据流水线无关；需要时再单独设计 |
| 性能基准（如"clean_signal 在 X 万行内 Y 秒"） | 依赖机器，易碎；D05 的性能验证留在 notebook 里做 |
| 真实数据行内容 | 合规（AGENTS.md 1.4），测试里出现的 IMSI 全是 `123456789012345678` 这类合成值 |

## 9. 维护约定

1. **改产品代码行为前**：先跑一遍测试。若契约测试失败，先判断"是改坏了"还是"承诺有意变化"——后者要同步更新契约测试和本文档，并在提交说明里写清契约变化。
2. **平台方改了 ODS 结构**：`--run-smoke` 对账 → 更新 `ods_schema.py` → 检查 pipeline 的 `SELECT *`。
3. **新增模块**：单函数行为进 `test/unit/`，跨模块承诺进 `test/contract/`；共享 fixture 放对应目录的 `conftest.py`，不建 `utils.py`（AGENTS.md 6.2）。
4. **提交格式**：测试改动按 AGENTS.md 14.2 用 `test: 一句话说明`。
