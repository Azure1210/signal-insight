## 3. 做得好的地方

1. **三层解耦，职责清晰**：`theme.py`（主题是什么/怎么注册）↔ `viz.py`（业务语义→颜色角色）↔ `config.py`（默认值）。新增主题只加 TOML，新增区域/客群只改 `viz.py` 一处，互不牵连。
2. **不可变数据类 + `derive`**：`Theme` 用 `frozen=True`，派生用 `dataclasses.replace`，`rc` 合并而非覆盖——换主题不产生脏状态。
3. **早校验**：颜色 `#RRGGBB` 正则、色图名存在性、色板非空、商业字体黑名单，全在主题**创建时**报错，而不是出图时才炸。
4. **状态色三件套**（通过绿 `ok` / 警告黄 `warn` / 不通过红 `alert`）：把「语义色」和「状态色」分开，红色只表示警示的纪律落实到位。
5. **`_rebind_imported` 的 identity 校验**：用 `is` 判断「名字相同且对象正是上次导出的那个」才重绑，既让 `from viz import MAIN` 跟随主题，又不会误改用户自己定义的同名变量——设计很克制。
6. **文档质量高**：两份文档分工明确（使用/扩展），含字段全表、合规红线、交付前检查清单，还有现成的 `preview_theme.py` 预览脚本。
7. **合规意识**：把商业字体（微软雅黑、苹方、Times、Arial…）列为红线直接拦截，这是很多教学项目会漏掉的点。

## 4. 发现的问题（按优先级）

### 🔴 高：`theme.py` 字体别名常量写错（确定 bug）— ✅ 已于 2026-10-10 修复

```python
CJK_SANS  = ( "Noto Serif CJK SC", "Source Han Serif SC")   # 应是黑体 Sans，写成了宋体 Serif
CJK_SERIF = ( "Noto Serif CJK SC", "Source Han Serif SC")
```

- `CJK_SANS` 是「黑体」组，却写了两条 **Serif（宋体）** 名字，且与 `CJK_SERIF` 完全相同。
- **后果**：`resolve_fonts` 注释里承诺的「衬线中文缺失时退到黑体」回退链失效——`CJK_SANS` 补进来的还是宋体；`has_cjk` 也因为两个 tuple 相同而退化。
- **在只装了思源黑体、没装宋体的机器上**：主题写的 `Noto Serif CJK SC` 找不到，回退链（也是宋体）也找不到 → 中文显示成方框，且 `apply_theme` 会误报「本机没有中文字体」，即使机器明明装了黑体。
- **为什么现在没暴露**：当前机器装了思源宋体，所以一切正常。这是典型的「潜伏 bug」。
- **预期写法**（与文档 §4.5 一致）：

  ```python
  CJK_SANS  = ("Noto Sans CJK SC", "Source Han Sans SC", "Noto Sans SC",
               "Noto Sans CJK JP", "WenQuanYi Zen Hei")
  CJK_SERIF = ("Noto Serif CJK SC", "Source Han Serif SC", "Noto Serif SC",
               "Noto Serif CJK JP")
  ```

### 🟠 中：文档与代码的字体描述不一致 — ✅ 已按「宋体 + Termes」修正文档

| 主题 | 代码实际 `fonts` | 文档描述 | 是否一致 |
|---|---|---|---|
| default | TeX Gyre Termes + Noto Serif CJK SC（衬线） | TeX Gyre Termes + 思源宋体 | ✅ |
| academic | TeX Gyre Termes + Noto Serif CJK SC（衬线） | TeX Gyre Termes + 思源宋体 | ✅ |
| business | **TeX Gyre Termes + Noto Serif CJK SC（衬线）** | **「TeX Gyre Heros + 思源黑体」（无衬线）** | ❌ |
| lively | 未写 `fonts`，继承 business（衬线） | 「思源黑体（中西文统一）」 | ❌ |

- `business` 代码里还是衬线（Termes=Times 替代 + 宋体），但文档说它是无衬线（Heros=Helvetica 替代 + 黑体）。
- `themes/lively.toml` 里那条字体注释下面**没有 `fonts = [...]` 行**，实际继承 business；但《主题使用说明》§3.4 说 lively 是「思源黑体统一」，《主题扩展指南》§5 的 lively 示例又写了 `fonts = ["Noto Sans CJK SC"]`。
- **判断**：大概率是「想改成无衬线」但代码没跟着改。需要明确 business/lively 到底用衬线还是无衬线，然后**文档与代码二选一对齐**。

### 🟠 中：`quality.py` 的可扩展性隐患

```python
old = pd.read_sql("SELECT * FROM dq_check_result", con)   # 每次全表读
...
new.to_sql("dq_check_result", con, if_exists='replace', index=False)  # 每次全表重写
```

- 每记一条稽核结果，就**全表读出、再全表写回**。检查项少时无所谓，但检查项一多就是 O(n²)，且整个表被反复重建。
- `except Exception` 捕获**所有**异常当「表不存在」处理，会掩盖真正的数据库错误（连接失败、权限、字段不匹配）。
- **建议**：改成「按 `check_id` 的 DELETE + INSERT」或 SQLite 的 `INSERT ... ON CONFLICT(check_id) DO UPDATE`（UPSERT）；判断表是否存在用 `sqlite_master` 查询，而不是裸 `except`。
- 另：`STATUSES = ("通过","警告","不通过")` 等逗号后缺空格（PEP8），`COLUMNS` 中英混排是 DB schema 约定，可接受。

### 🟡 低：若干小问题（可后续处理）

1. **`_rebind_imported` 成本与可移植性**：依赖 `sys._getframe`（CPython 专用），且每次 `apply_theme` 都要遍历全部 `sys.modules` + 调用栈。功能正确、设计克制，但属于「重手段」，PyPy 等实现不可用。若目标环境固定为 CPython 可暂不动。
2. **`Theme.resolve("cat:abc")` 抛裸 `ValueError`**：`int()` 报错信息不友好，可改为明确提示。
3. **文件头模板**：`config/theme/viz/quality.py` 都带 `#!/usr/bin/env python` 和 `# -*- coding: utf-8 -*-`，对模块（非脚本）没必要（PyCharm 模板自带）。无害，仅风格。
4. **`resolve_fonts` 每次调用都 `installed_fonts()`**：扫一次 `ttflist` 不便宜，`apply_theme` 时只发生一次，暂可接受。
5. **`lively` 第 3、6 分类色同色系**（薄荷 / 深薄荷，靠明度区分）：文档已提示「同图时建议线尾标注」，是有意识的取舍，不算 bug。

## 7. 附：quality.py 宽泛异常捕获的重构方案（本期不改代码，仅留存）

> 决策（2026-10-10）：`quality.py` 暂不修改，后期再改；先把 `except Exception` 的重构方案写清楚，届时直接照做。

### 问题

```python
try:
    old = pd.read_sql("SELECT * FROM dq_check_result", con)
except Exception:
    old = row.iloc[0:0]
```

`except Exception` 把「表不存在」和「连接失败 / 权限不足 / SQL 语法错」混为一谈：真正的错误被静默吞掉，只剩下空 DataFrame，随后 `to_sql(..., if_exists='replace')` 会悄悄覆盖整张表，问题很晚才暴露。

### 方案 A（推荐，根治）：UPSERT，不再先读全表

给 `check_id` 加唯一约束，用一条 `INSERT ... ON CONFLICT DO UPDATE` 完成「新增或覆盖」，从根上同时消除「先读全表」和「宽泛捕获」。

```sql
-- 建表时给 check_id 加 UNIQUE 约束
CREATE TABLE dq_check_result (
    check_id TEXT UNIQUE,
    ...其它字段...
);
```

```sql
INSERT INTO dq_check_result (check_id, 维度, 检查项, 表字段, 结果, 状态, 证据, 处理决定)
VALUES (?, ?, ?, ?, ?, ?, ?, ?)
ON CONFLICT(check_id) DO UPDATE SET
    维度 = excluded.维度, 检查项 = excluded.检查项, ...;
```

### 方案 B（最小改动）：精确判断表是否存在

```python
def _table_exists(con, table: str) -> bool:
    sql = "SELECT 1 FROM sqlite_master WHERE type='table' AND name=?"
    return pd.read_sql(sql, con, params=(table,)).shape[0] > 0

old = (pd.read_sql("SELECT * FROM dq_check_result", con)
       if _table_exists(con, "dq_check_result") else row.iloc[0:0])
```

### 方案 C（兼容多数据库）：只捕获「表不存在」这一种错误

```python
try:
    old = pd.read_sql("SELECT * FROM dq_check_result", con)
except pd.errors.DatabaseError as e:
    if "no such table" in str(e).lower():   # SQLite 的「表不存在」特征串
        old = row.iloc[0:0]
    else:
        raise                                # 其他数据库错误照常抛出，不吞
```

### 建议

- 一步到位 → **方案 A**（同时解决全表重写 + 宽泛捕获）。
- 最小改动 → **方案 B**，避免裸 `except Exception`。
- 多数据库 → 方案 C 作备选。
