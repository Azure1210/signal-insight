2. 第二天：我们发现要写notebook，你得复制很多第一天的内容，于是决定对前面写过的代码进行抽象和封装
   1. 一个很自然的问题，抽象的脚本应该放在什么地方？
      1. 第一种做法：一种放在和notebook脚本的目录，或者单独建立一个目录存放这些抽象、这样做的问题是: notebook当中运行非常麻烦：``%run  xxxxx.py`一旦脚本位置发生变化，这些命令直接失效，因此放弃这种做法
      2. 第二种做法：参照网上的教程：使用`import sys, sys.insert("0, 脚本的路径")`说白了就是把脚本路径放到解释器的查找路径的当中，这种方法的问题是：你几乎每个脚本都要写这样的东西，很麻烦
      3. 第三种做法：把脚本做成可以安装的包，这样子就可以在当前的虚拟环境当中随便导入。在这我们学习了如何做一个python并进行自定义的安装，这就是为什么要在那里做 `pyproject.toml`文件的创建，还有`pip install -e . `
   2. 确定了采用自定义装包的方式，我们开始进行抽象和封装
3. 封装的第一个脚本:`config.py`封装的过程发现了一些问题
   1. `config.py`当中我们定义了一些路径,其中项目的根路径，我们最开始是采用`.parents`方法来找项目的跟路径的,但是找的时候发现一些问题，一旦`config.py`位置发生变动里面定义的路径就全部失效了.
   2. 所以关于`config.py`失效的问题，我们采用 标记文件查找法，在项目的跟路径放置一个文件`signal.workspace`文件，然后在`config.py`中定义一个函数进行查找，这样子不管`config.py`在项目的什么位置，都可以准确的找到项目的根路径
4. 封装的第二个脚本：可视化函数的封装: `viz.py`说白了就是定义了一系列的常量参数，颜色配置，字体设置，一个主题`apply_theme`，以及图表标题，副标题，来源相关的函数`finish`函数.封装完成之后能不能用呢？能用，但是我们贪了一手，考虑到不同的使用场景需要不同的主题，所以我们借助大模型做了一次重构，功能是实现了，而且是那种插拔设计，添加一种主题，只需要写一个`toml`文件，但是这个也存在不好的地方，大模型写了很多内容，导致脚本维护很困难，所以当前的现状是：可视化相关的内容：可以稳定运行，可以友好扩展，但是内容是由大模型写的，很难维护，因为单个脚本内容太多了，不符合**单一原则，高内聚低耦合**，关于这部分未来需要重构。需要进行解耦和拆分操作，然后理解这种架构是怎么设计的，为什么他可以通过新建`toml`文件来增加不同的主题，他是怎么识别到这个文件并增加主题的，还有他的字体检测机制是必须的吗？
